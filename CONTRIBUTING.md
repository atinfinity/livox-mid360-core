# Contributing

Thank you for helping with `livox-mid360-core`. This page covers the checks a change has to pass
and how to run them locally. The build itself is in the [README](README.md#build); the design
is in [docs/architecture.md](docs/architecture.md) and the per-layer pages next to it; open
work and project decisions are in [docs/roadmap.md](docs/roadmap.md).

## Ground rules

- **Clean room.** The library is written from the public Livox protocol wiki only. Do not copy
  or paraphrase code from Livox-SDK2 or other drivers; use them solely to compare behaviour
  on hardware. Record wiki ambiguities and their resolution in
  [docs/protocol_notes.md](docs/protocol_notes.md).
- **Scope.** Base Mid-360, Ubuntu 24.04+, no third-party runtime dependencies. See the
  decisions table in [docs/roadmap.md](docs/roadmap.md#project-decisions) before proposing
  something outside that.
- **Issues first.** Every feature and design decision has an issue; link it from the PR and
  record the decisions taken in the issue or the matching `docs/` page. Labels: `no-hardware`
  (doable against the simulator), `needs-hardware`, `phase-2` / `phase-3`, `good first issue`.
- **Tests.** Protocol changes need golden vectors regenerated by `tools/gen_golden_vectors.py`
  (CI fails on a diff), transport / session / device changes need a simulator-driven test in
  `tests/`, and anything asynchronous must stay green under ASan + UBSan on a 2-vCPU runner.
  Keep simulator data rates low in tests (see `tests/test_reconnect.cpp`).
- **Errors, not exceptions.** Fallible calls return `std::expected`; the library never writes
  to stdout or stderr.

## Lint

Style and static analysis are enforced by the `Lint` workflow (clang-format 19, clang-tidy 19,
ruff). The configuration files `.clang-format`, `.clang-tidy` and `pyproject.toml` are shared
with `livox-mid360-ros2` (`ament_clang_format --config`, `ament_flake8 --config`).

C++ follows the [ROS 2 C++ style](https://docs.ros.org/en/rolling/The-ROS2-Project/Contributing/Code-Style-Language-Versions.html#c):
`.clang-format` is a verbatim copy of the configuration shipped with `ament_clang_format`
(the commit is named in the file header) and is re-synced by hand, not by CI. On top of the
formatter, clang-tidy's `readability-braces-around-statements` requires braces on every
`if` / `for` / `while` body. Deviations from the ROS 2 rules: `#pragma once` instead of include
guards (so cpplint is not used, #17), and no cpplint-style header/footer comments. Code blocks in
the documentation follow the same style. Run the same checks locally with:

```sh
scripts/lint.sh            # check (clang-tidy needs clang-19 and builds build-tidy/)
scripts/lint.sh --fix      # apply clang-format and ruff fixes
scripts/lint.sh --no-tidy  # formatting only
```

## Fuzzing

Eight libFuzzer targets live in `tests/fuzz/`: the protocol parsers (`fuzz_command_frame`,
`fuzz_data_packet`, `fuzz_key_value_list`), the endpoint text parser (`fuzz_transport_text`),
the session helpers that turn a received datagram into a result (`fuzz_session_ack`,
`fuzz_discovery_ack`, via the internal `src/session_detail.hpp`) and the whole `Session`
request loop driven over a loopback socket pair (`fuzz_session_loopback`: the input selects
the call, the retry count and the reply datagrams, which are queued before the call so no
threads are involved) and the frame assembler fed with synthesised packet headers
(`fuzz_frame_assembler`, via the internal `src/frame_assembler.hpp`). Each target has a seed corpus in `tests/fuzz/corpus/<target>/`,
generated by `tools/gen_fuzz_corpus.py` from the
Python reference implementation and kept in sync by CI. Build with Clang and run all of them:

```sh
cmake -S . -B build-fuzz -G Ninja -DCMAKE_BUILD_TYPE=Debug -DCMAKE_CXX_COMPILER=clang++-19 \
      -DLIVOX_MID360_BUILD_FUZZERS=ON -DLIVOX_MID360_ENABLE_ASAN=ON -DLIVOX_MID360_ENABLE_UBSAN=ON
cmake --build build-fuzz --target fuzzers
scripts/fuzz.sh build-fuzz 30   # seconds per target; CI runs the same script
```

## Coverage

The `Coverage` workflow builds with GCC 14 and `LIVOX_MID360_ENABLE_COVERAGE=ON`, runs the
Catch2 suite and uploads a gcovr report to [Codecov](https://codecov.io/gh/atinfinity/livox-mid360-core)
(README badge, line coverage). The HTML report is attached to each run as the `coverage-html`
artifact. Locally (`gcovr` from apt or pip):

```sh
cmake -S . -B build-cov -G Ninja -DCMAKE_BUILD_TYPE=Debug -DLIVOX_MID360_ENABLE_COVERAGE=ON
cmake --build build-cov && ctest --test-dir build-cov
gcovr --root . --txt-metric branch --filter 'src/.*' --filter 'include/livox/mid360/.*' \
      --exclude 'tests/.*' --exclude 'build.*/.*' --html-details coverage.html --print-summary
```

Counted: `src/` and `include/livox/mid360/`. Excluded: tests, fuzzers, generated golden
vectors, Catch2, and the non-Linux fallback branches in `src/transport.cpp` (marked with
`GCOVR_EXCL_START` / `GCOVR_EXCL_STOP`, since CI measures on Linux). Branch coverage is
reported but the badge and the Codecov status checks use line coverage; both checks are
informational for now.

## Continuous integration

`CI` runs gcc-13, gcc-14 and clang-19 in Release plus gcc-14 and clang-19 in Debug with
ASan + UBSan, each on x86-64 and arm64 (`ubuntu-24.04-arm`), and separate jobs for the Python
reference and simulator tests and a short run of every fuzzer. `Lint` runs clang-format 19,
clang-tidy 19 and ruff; `Coverage` uploads to Codecov.

To reproduce CI locally on any Docker host: `docker/check.sh [linux/arm64|linux/amd64]`. The
platform defaults to the host's. On Apple Silicon `linux/arm64` runs natively; a non-native
platform runs under QEMU emulation, where the script only does the Release builds, `ctest` and
the Python tests and skips the sanitizer and fuzz steps. `docker/check.sh` runs the linters
before the builds, so it is the one-stop pre-push check.

## Pull requests

- One issue per PR where possible; title in the conventional style used in the history
  (`feat(device): ...`, `fix: ...`, `docs: ...`, `ci: ...`, `test: ...`).
- Update the documentation that describes what you changed in the same PR: the per-layer page
  in `docs/`, `docs/architecture.md` if threads, locks or data flow moved, and
  `docs/roadmap.md` when an issue is finished.
- PRs are squash-merged; the PR title becomes the commit subject.
